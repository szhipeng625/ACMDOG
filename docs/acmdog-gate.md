# ACMDOG 门禁与端到端测试说明

本文档说明仓库当前 CI 门禁的设计、覆盖范围、运行方式与已知限制。

## 一、目标

每次向 main 分支提交或发起合并请求时，自动执行一组检查。任何一项失败，整体判定失败，合并请求无法合入 main。

核心诉求：代码改动必须能编译、配置必须合法、业务链路必须真实跑通。

## 二、用例清单

门禁入口为 tests/run_tests.sh，共 12 项检查，分四类：

### 1. 静态完整性检查（5 项）

- workflow_yaml_valid：流水线定义文件格式合法
- lsm_binary_present：部署二进制 lsm_server 存在
- lsm_binary_elf：该文件是有效的 Linux ELF 可执行文件
- lsm_binary_hash：其 SHA256 与记录值一致，未被悄悄替换
- lsm_config_toml：deploy/lsm/config.toml 为合法 TOML

### 2. 编排与网关检查（4 项）

- compose_yaml_valid：两份 docker-compose 文件可被 YAML 解析
- compose_middleware：middleware 编排文件结构合法
- compose_nginx：nginx 编排文件结构合法
- nginx_config_syntax：用容器对整套 nginx 配置执行 nginx -t，验证语法与加载

说明：nginx 配置引用了证书目录下的文件，检查时会在临时目录生成自签证书与临时参数文件补齐依赖，避免因缺少证书导致误报。

### 3. 编译检查（1 项）

- cloud_judge_build：用 CMake 完整编译评测组件，含编排与沙箱执行两个可执行程序

### 4. 业务验证（2 项）

- lsm_business_smoke：临时拉起存储服务，验证端口就绪、探活、写入、读回、删除、删除后查询为空，结束后销毁临时目录
- e2e_full_chain：端到端全链路验证，详见下节

## 三、端到端全链路用例

位置：tests/e2e/test_full_chain.py

它模拟一个真实用户提交，让请求走完整条业务链路，而不是只检查文件格式。

### 执行步骤

1. 环境就绪检测：逐个确认消息队列 5672、存储服务 6380、业务中间件 8898、编排服务 8890 在监听，评测容器内编译器可用
2. 投递任务：按题解文件与题目编号组装评测任务，投递到任务队列
3. 取题：评测消费端从业务中间件拉取题面与生成器配置
4. 生成数据：按题目关联的生成器编译并运行，产出各组测试输入
5. 编译题解：编译用户提交的代码
6. 逐点判题：对每组数据运行并比对输出
7. 回传结论：结果写入结果队列，同时编排服务保留任务终态

### 判定标准

- 必须拿到明确的终态结论（AC / WA / CE 等），中间态不算通过
- 测试点数量必须大于等于 1，且全部为 AC 才算通过
- 必须上报资源数据（CPU 纳秒数）
- 队列取不到回执时，回查编排服务核对终态，避免消息时序造成误判
- 任何一步失败即整体失败

## 四、运行方式

### 本地手动运行

```bash
bash tests/run_tests.sh
```

逐阶段结果实时打印，同时写入 tests/out/run.log，汇总在结尾输出。全部通过退出码为 0，任一失败退出码为 1。

### 单独运行端到端用例

```bash
python3 tests/e2e/test_full_chain.py
```

### 流水线运行

推送到 main 或对 main 发起合并请求时自动触发，步骤为：检出本次提交的代码 → 运行全部用例 → 写运行摘要 → 上传日志产物（保留 30 天）。

日志与摘要作为产物留存，成功也上传，失败时可直接下载现场。

## 五、环境依赖

以下依赖需在 runner 所在机器上预先就绪：

| 组件 | 端口 | 说明 |
| --- | --- | --- |
| 消息队列 | 5672 | 任务队列与结果队列 |
| 存储服务 | 6380 | 项目自带存储服务 |
| 业务中间件 | 8898 | 提供题面与题目数据 |
| 编排服务 | 8890 | 评测编排与任务状态查询 |
| 测试数据库 | 3306 | 题目数据与业务表 |
| 编译器 | - | 评测容器内需具备 g++ |

## 六、已知限制

1. 题目数据依赖：端到端用例复用测试库中已有的题目数据，换机器或清库后需重新导入样本，否则该用例会因取不到题目而失败。

2. 依赖预先就绪：上述端口上的服务需事先运行。用例会检测并明确报告哪一环未就绪，但不负责自动拉起全部依赖。

3. 单题覆盖：端到端用例当前固定验证题目 111，尚未覆盖全部题目。

4. 评测容器编译器：已在镜像构建文件中固化 g++，但只有重新构建镜像后才生效；沿用旧镜像时仍需临时补装。

5. 测试脚本防篡改：用例与业务代码同仓，靠分支保护与 CODEOWNERS 审批约束，技术上无法完全阻止有写权限者修改用例。

## 七、维护要点

- 新增检查：在 tests/run_tests.sh 中追加一行 run_case 即可，命名保持语义清晰
- 修改判定标准：调整对应脚本的退出码逻辑，失败必须返回非零
- 二进制更新：替换 deploy/lsm/lsm_server 后需同步更新 .github/lsm-server.sha256，否则哈希检查会失败
- 题目变更：更换验证题目时，同步修改 tests/e2e/test_full_chain.py 中的题目编号与对应题解
- 运行产物：build/ 与 tests/out/ 已在忽略规则中排除，不会进入版本库
